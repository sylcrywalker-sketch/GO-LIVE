# PC State / Boot Backend — Stage 2A

Внутреннее состояние стартового ПК: какие детали установлены, включится ли он, дойдёт ли до рабочего стола, есть ли видеокарта и хватает ли блока питания. Desktop, браузер, Streamly, Critical Strike, интернет и периферия в этот этап не входят и строятся поверх этого слоя.

## 1. Ответственность

| Класс | Отвечает за |
| --- | --- |
| `PcAssembly` (plain C#) | Единственный владелец записи «слот → InstanceId». Правила совместимости (тип + разъём), монтаж слотов (`PcSlotSpec.HostSlotId`), снимок для сохранения. |
| `PcCapabilities` (plain C#, значение) | Что ПК может, вычисляется из `PcAssembly` при каждом чтении: наличие деталей, бюджет мощности, `CanPowerOn`, `CanUseDesktop`, `GamingGraphicsAvailable`, `CanPlayCriticalStrike`, упорядоченные диагностики. Не кэшируется. |
| `PcDiagnostic` (plain C#, значение) | Код + серьёзность (`Blocker`/`Limitation`) + что именно затронуто (`PcFunction.PowerOn/Desktop/Gaming`) + ключи локализации + ватты (только `InsufficientPower`). Таблица значений — `PcDiagnostic.For`. |
| `PcPowerOnResult` (plain C#) | Ответ на нажатие кнопки питания: `Blocked`/`Started`, `ReachesDesktop`, текущие capabilities. Без состояния: в игре пока нечему «работать» после включения, поэтому On/Off не хранится и не сохраняется. |
| `PcComponentSpec` (ScriptableObject, только данные) | Тип, разъём, потребление; у блока питания — мощность. `Validate` отвергает невозможные данные. |
| `PcAssemblyBehaviour` (мост Unity) | Слоты сцены, новые детали новой игры (`preinstalled`), две транзакции руки ↔ слот, load. Владелец начальной сборки. |
| `PcComponentSlot` (авторинг слота) | ID, тип, разъём и `mountedOn` (на каком слоте стоит) уходят в `PcSlotSpec`; остальное — презентация: поза установки, область указателя, подсветка, `hiddenWhileFilled` (заглушки) и `installedWith` (кулер процессора виден только с процессором). |
| `PcWorkbenchText` (plain C#) | Все тексты режима сборки: вердикт, одна строка объяснения, чек-лист деталей, карточка слота, заметки панели деталей и их порядок, причины отказа с названиями деталей. Состояния не хранит. |
| `PcWorkbenchBehaviour` | Режим, ввод, цель указателя, транзакции через мост. Правил ПК и текстов не содержит. |

## 2. Правила

- `CanPowerOn` = материнская плата + процессор + ≥1 модуль памяти + блок питания + `TotalPowerDrawWatts ≤ PowerSupplyCapacityWatts`.
- Накопитель для включения не нужен; `CanUseDesktop` = `CanPowerOn` + накопитель.
- Без видеокарты ПК включается и доходит до рабочего стола; `GamingGraphicsAvailable` = `CanPowerOn` + видеокарта; `CanPlayCriticalStrike` = `CanUseDesktop` + `GamingGraphicsAvailable`.
- Мощность не влияет на физическую установку: деталь ставится в подходящий слот, а слабый блок питания даёт `InsufficientPower` и блокирует включение.
- Порядок диагностик фиксирован (`PcDiagnosticCode`): MissingMotherboard, MissingCpu, MissingMemory, MissingPowerSupply, InsufficientPower, MissingStorage, NoDedicatedGpu. Каждая — не больше одного раза. Отсутствующий блок питания — `MissingPowerSupply`, а не `InsufficientPower`. `PcDiagnostic.Component` — деталь, о которой находка.

### Монтаж слотов (материнская плата)

- Слот может стоять на другом слоте (`PcSlotSpec.HostSlotId`, в префабе — `PcComponentSlot.mountedOn`). Процессор, память и видеокарта стоят на `motherboard-0`; блок питания и накопитель — на корпусе.
- Слот без установленной хост-детали не существует (`PcAssembly.IsSlotPresent`): установка в него — `PcSlotCheck.HostMissing` («Сначала установите материнскую плату»), указатель и подсветка его не видят, чтобы он не закрывал место самой платы.
- Хост-деталь снимается только когда на ней ничего не стоит: иначе `PcSlotCheck.MountedPartsInstalled`, а `PcAssembly.InstalledOn(slot)` перечисляет, что снять сначала («Сначала снимите процессор и оперативную память»).
- Снятая плата — тот же `ItemInstance`: Installed → Carried → Inventory и обратно, как любая деталь.
- Сохранение, где деталь записана в слот без хоста, отвергается до изменения живого состояния (`IsValidSnapshot`); то же правило проверяет стартовый набор.
- Правило общее: в коде нет условий по материнской плате, всё задаётся данными слотов (доменные тесты используют отсек накопителя с двумя картами).

## 3. Стартовый ПК (новая игра)

| Слот | Тип / разъём | Деталь (ItemId) | Вт |
| --- | --- | --- | --- |
| `motherboard-0` | Motherboard / MotherboardTray | `starter-motherboard` | 25 |
| `cpu-0` (на плате) | Cpu / CpuSocket | `starter-cpu` | 65 |
| `ram-0` (на плате) | Ram / MemorySlot | `starter-ram` | 3 |
| `psu-0` | Psu / PowerSupplyBay | `used-psu` (существующий товар) | ёмкость 300 |
| `storage-0` | Storage / SataStorage | `starter-hdd` | 6 |
| `gpu-0` (на плате) | Gpu / PcieX16 | пусто; `budget-gpu` из магазина | 75 |

Итого 99 Вт; с Budget GPU 174 Вт из 300. Детали — реальные `WorldItem` внутри префаба `StudentPC` на `InstallAnchor` своих слотов, с постоянными scene ID (`authoredInstanceId`), и перечислены в `PcAssemblyBehaviour.preinstalled`.

Жизненный цикл: `WorldItem.Awake` создаёт `ItemInstance` (World) → `PcAssemblyBehaviour.Awake` строит слоты → `PcAssemblyBehaviour.Start` (Unity вызывает все Awake загруженной сцены до любого Start) проверяет весь набор целиком тем же `IsValidSnapshot`, что и загрузка, плюс правила сцены (деталь на якоре своего слота, неучтённых предметов на якорях нет, scene ID есть и уникален), и только потом переводит предметы World → Installed и записывает сборку. Ошибка контента: лог, ПК выключен, ничего не сдвинуто. `Start` выполняется один раз; включение/выключение объекта ничего не дублирует. Сохранение/загрузка требуют `PcAssemblyBehaviour.IsReady`.

## 4. Сохранение — v6

Item system хранит InstanceId, DefinitionId и `Installed`; `PcAssembly` хранит SlotId → InstanceId. SlotId в `ItemSaveData` нет, позы у установленных деталей нет (её задаёт слот). Схема поднята до **v6**: сохранения v1–v5 не содержат стартовых деталей, и при загрузке сцены-предметы, отсутствующие в сохранении, стали бы `Removed` — ПК молча лишился бы процессора и памяти. Поэтому v1–v5 отвергаются до изменения живого состояния, миграции нет (pre-release).

## 5. Режим сборки: что показывает экран

- Статус: заголовок «Состояние ПК», вердикт (`Не включится` / `Не загрузится` / `Готов к работе` / `Готов к играм и стримам`), одна строка о самой важной находке, затем по строке на каждый тип слота: ● на месте, ○ нет, ▲ есть, но не справляется; красный — мешает ПК работать, янтарный — только ограничивает. Каждый факт — один раз (недостающие детали вместе дают строку «Установите отмеченные детали»).
- Карточка слота: человеческое название детали, затем установленная деталь и технический ярлык (`Старый процессор · CPU socket`), затем действие клавиш или причина отказа.
- Панель деталей — тот же `PlayerInventory`: сначала то, что можно поставить сейчас, затем другие детали ПК с короткой причиной, остальное приглушено. Порядок только в панели (`InventoryListView.SetRowOrder`), порядок инвентаря не меняется.
- Ракурс: плата почти анфас (12° по горизонтали, 15° вниз), корпус ~63 % высоты кадра 16:9, центр x ≈ 0.41, лицевая панель корпуса — узкая грань справа.

## 6. Ограничения этапа

- Один слот памяти (`ram-0`), хотя на модели платы два DIMM; второй модуль покрыт доменными тестами.
- Кулер процессора — не предмет: он виден только пока процессор установлен (`installedWith`). Вентилятор и кабели — статичная презентация корпуса.
- Модель б/у блока питания (102 мм) выше ATX-отсека корпуса (87 мм), поэтому `Visual` в `Item_UsedPowerSupply` равномерно масштабирован до 0.845 (86 мм, ATX-высота). FBX не менялся; иконка от равномерного масштаба не меняется.

## 7. Тесты

- `PcAssemblyTests` (plain C#): совместимость, запись, снимки, монтаж слотов (хост ставится первым и снимается последним, снимок без хоста отвергается, хосты заканчиваются на корпусе).
- `PcCapabilitiesTests` (plain C#): 13 обязательных случаев, мощность, порядок, спецификации, попытка включения.
- `PcPreinstalledPartsTests` (EditMode, настоящий префаб): каждая ошибка начального контента отвергается целиком, включая детали без своей платы.
- `PcBuildingContentTests`: таблица слотов с хостами, кулер с процессором, стартовые детали, уникальные ID, мощность, только ПК-детали имеют спецификацию, локализация RU/EN.
- `PcBuildingPlayModeTests` (настоящий префаб, Play Mode): сценарии A–F, save/load, 18 видов порчи сохранения, плата снимается только после процессора, памяти и видеокарты и сохраняет свой InstanceId.
- `PcWorkbenchPlayModeTests` (реальная сцена GL): режим сборки, кадрирование, панель деталей, плата через Workbench.

Play Mode-тесты — это EditMode-тесты, которые сами входят в Play Mode: Test Runner шагает их по обновлениям редактора, а не по кадрам игры. Поэтому ожидания считают кадры игры (`PlayModeWait.Frames`) или ждут само условие (`PlayModeWait.Until`) и через 10 с говорят, что Play Mode не идёт. Виртуальные клавиатура и мышь — `VirtualInput`: он владеет только тем, что меняет (свои устройства, две настройки Input System, включённость остальных устройств на время теста), и возвращает ровно это; настоящие устройства никогда не удаляются.
